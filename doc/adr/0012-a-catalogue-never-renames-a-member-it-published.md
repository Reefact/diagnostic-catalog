# ADR-0012 | A catalogue never renames a member it published

**Status:** Accepted
**Proposed:** 2026-07-30
**Accepted:** 2026-07-30
**Decision Makers:** Reefact

## Context

A generated catalogue publishes two kinds of member a consumer writes by hand: a
rule class, referenced as `SonarRule.S1144.Id`, and a category constant,
referenced as `SonarCategory.MajorCodeSmell`. Both appear in the consumer's own
source, inside `SuppressMessageAttribute` arguments.

The rule members carry an identifier the vendor chose, so their names follow
upstream and cannot drift on their own. The category members do not: a vendor
category is a free-text string — `"Major Code Smell"`, `"StyleCop.CSharp.SpacingRules"`
— and this repository derives a C# identifier from it. Distinct strings can
derive the same identifier, so the derivation includes a disambiguation step, and
which of two colliding categories keeps the plain name is decided by the order
they are processed in.

Catalogue content is regenerated by an unattended nightly job whose output is a
pull request for review (ADR-0009, §14.3). A reviewer reads that diff as a
statement about upstream: rules added, rules retired, categories introduced. A
member being *renamed* is not a shape the diff announces.

§23.1 and ADR-0010 already record the sibling guarantee for rule constants: one is
never deleted, because consumers inline constant values at their own compile time
and a member that vanishes breaks their recompilation. No equivalent statement
covered the names of the category constants beside them.

A renamed member is a compile error for every consumer that referenced it. Unlike
a wrong category value — which the .NET platform never reads, and which therefore
changes no behaviour — a rename cannot be absorbed silently: it stops builds.

## Decision

A catalogue never renames a member it has already published; a member's name, once
released, is fixed for the life of that catalogue's major version.

## Rationale

The value this library offers is that a reference to a rule is a contract the
compiler checks. A contract whose member names can move underneath a consumer is
not a contract; it is a stronger-looking version of the magic string it replaced,
because the consumer now believes the compiler is guarding them.

The guarantee has to be absolute rather than best-effort, for the same reason
ADR-0010 makes deletion impossible rather than rare. The rename would arrive
through the nightly job — unattended, at night, in a pull request whose diff is
read as a report about upstream rather than about this repository's own naming.
A reviewer who is not specifically looking for a rename will not see one. Any
guarantee that depends on that reviewer is not a guarantee.

Deriving names deterministically is not sufficient on its own: determinism means
the same inputs give the same names, and the inputs change every time upstream
adds a category. Stability across *different* inputs is the property required, and
it can only come from the previous output being an input to the next.

The cost is accepted: a name published under disambiguation keeps its
disambiguated form even after whatever collided with it disappears. That leaves a
catalogue carrying an occasional name that reads worse than it needs to. Tidying
it would mean renaming a published member — precisely what this decision forbids —
so the cosmetic debt is the correct thing to pay.

The guarantee is bounded by the major version, matching how this repository already
treats identifiers: renaming or removing a symbolically referenced member is a
breaking change (CLAUDE.md), which a major release may make deliberately and
visibly. What this decision removes is the *accidental* rename, not the considered
one.

## Alternatives Considered

### Record each catalogue's public API surface and fail the build when it changes

`Microsoft.CodeAnalysis.PublicApiAnalyzers` already guards the foundation's own
surface, and its record includes constant values, so a renamed or revalued member
would in principle be flagged.

Rejected on three grounds. The generated source file *is* the public API record —
committed, diffable, and the actual source — so a second file would be a lossy
copy to be kept in agreement with it. The surface is large enough that the record
would be several thousand generated lines across the catalogues. And the nightly
job makes the mechanism self-defeating: if the job regenerates the record, nothing
is ever flagged; if it does not, every nightly pull request arrives failing, with
the entries to reconcile by hand.

Decisively, it would not have prevented the rename it was considered for. A
regenerated record accepts a new name as readily as it accepted the old one; it
reports that the surface changed, having already agreed to the change.

### Accept the rename and document it as a breaking change

Renames could be permitted and simply surfaced — in the nightly pull request body,
in the changelog, in the release notes.

Rejected because the event does not originate in a decision anyone makes. Nobody
chooses to rename a category constant; it happens because an unrelated category
arrived upstream and sorted a certain way. Documenting an accident does not make
it intentional, and it would put every consumer's build at the mercy of a vendor's
choice of punctuation.

### Derive names that cannot collide

A derivation preserving more of the original string — punctuation encoded rather
than stripped — would make collisions impossible and the ordering question moot.

Rejected because it trades a rare problem for a permanent one: every category
constant would carry an awkward name to protect against a collision that mostly
does not occur. It would also rename every existing constant on introduction,
which is the very outcome being designed out.

## Consequences

### Positive

* A consumer's reference to a category constant keeps compiling across catalogue
  updates within a major version.
* The nightly job cannot introduce a rename, so its pull requests can be read as
  what they claim to be: a report about upstream.
* The guarantee for rule constants (ADR-0010) and for the categories beside them
  are now the same promise, rather than one written down and one assumed.

### Negative

* A catalogue can carry a disambiguated name after the collision that caused it
  has gone. The name is uglier than it needs to be, permanently.
* Generating a catalogue now depends on reading its previous output, so the two
  halves of the generator are coupled more tightly than before.

### Risks

* The guarantee holds only while the previous output can be read back. If that
  recovery ever broke, every run would look like a first run and the protection
  would stop applying **silently** — the failure mode this repository exists to
  design out. It is covered by tests, and that coverage is load-bearing rather
  than incidental.
* A catalogue file rewritten by hand, or lost and regenerated from nothing, starts
  over with no memory of what it published. Regeneration is scripted precisely so
  this does not happen, but nothing in the build prevents it.

## Follow-up Actions

* None. The guarantee is enforced by the generator and covered by tests; there is
  no separate check to add.
