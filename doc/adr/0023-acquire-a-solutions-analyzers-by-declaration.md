# ADR-0023 | Acquire a solution's analyzers by declaration, never by discovery

**Status:** Proposed
**Proposed:** 2026-08-01
**Decision Makers:** Reefact

## Context

`dcat` acquires the analyzers a catalogue mirrors from one of five kinds of source: a
package on a feed, a package file on disk, a project, a set of already-built assemblies,
and a solution.

The first four name what to read. A solution does not. It lists projects of every kind —
libraries, tests, tooling, samples — and only some of them produce the analyzers whose
descriptors a catalogue is generated from (ADR-0009). Something has to decide which, and
the decision cannot be avoided by reading all of them: a project that produces no
descriptors is not merely uninteresting to read, it is a project whose output may not
exist, whose construction may throw, and whose evaluation costs a spawned MSBuild.

Two signals are the obvious candidates for inferring the set. Measured on this repository
at the time of writing:

| Signal | Projects matched | Of which produce catalogued rules |
|---|---|---|
| A direct reference to a Roslyn API package | 6 | 1 |
| A type deriving from `DiagnosticAnalyzer` | 2 | 1 |

The first row counts a reference to the compiler API a project would need in order to
*write* an analyzer, and not the `Microsoft.CodeAnalysis.*` packages that are themselves
analyzers a project merely runs — a distinction a heuristic reading package names would
have to make, and which changes the count.

The second signal's one wrong match is a test fixture whose constructor throws on purpose,
which exists precisely to exercise how the tool survives an analyzer that cannot be
constructed.

ADR-0010 records that a rule which disappears from the source is carried forward as
`[Obsolete]` rather than deleted, because a consumer's compiler inlines the `const` value
and deleting it would break code that has already shipped. A rule that was never read and
a rule the vendor retired therefore reach the output in the same shape, and nothing
downstream — not the emitted file, not the exit code, not the diff a reviewer sees —
distinguishes them.

The catalogues in this repository are regenerated by scheduled jobs (ADR-0017 publishes
the tool for exactly that use). Such a job reports an exit code and, when something moved,
a pull request; it has no reader watching a console.

The generator locates a project's output by evaluating its MSBuild properties. That
evaluation restores nothing, builds nothing and writes no intermediate output, which is
what allows a catalogue to be validated against a working copy without disturbing it.

MSBuild already carries a property that resembles the statement being sought,
`EnforceExtendedAnalyzerRules`. In this repository one project sets it and declares no
`DiagnosticDescriptor` at all.

This repository already decides two other memberships by a declaration inside the
project's own file rather than by a list kept elsewhere: which release train a project
ships on (ADR-0002, ADR-0007), and whether a test project runs on the .NET Framework
floor (ADR-0001).

## Decision

When a catalogue is generated from a solution, `dcat` reads exactly the projects that
declare they produce diagnostic rules, and never infers which projects might.

## Rationale

The decision rests on the two errors not being comparable. Reading a project that produces
nothing costs a wasted evaluation and contributes no descriptors; reading one project too
few removes rules from the catalogue, and ADR-0010 then turns that removal into a published
claim that those rules were retired. The consumer is told, by a deprecation warning the
compiler raises on their own code, something that is not true — about a vendor that still
ships the rule. No signal anywhere reports it: the run succeeds, and the diff looks exactly
like the upstream retirements the tool is built to carry forward correctly. A heuristic
tuned to reduce the harmless error necessarily increases the harmful one.

No candidate signal is close enough for that trade to be worth making. Both are wrong by a
multiple, and in opposite directions, on the one solution whose answer is already known.
The wrong matches are also not noise that a filter could remove: the fixture that derives
from `DiagnosticAnalyzer` is a deliberately unconstructible type, so the more precise of
the two heuristics selects, as its single false positive, the exact input that takes the
descriptor-reading worker down. A heuristic whose failures cluster on the pathological
cases is not a heuristic that needs refining.

The deeper objection is that a heuristic's accuracy cannot be assessed where it is used.
Measuring it here is measuring it on the one solution whose right answer is known; the
solutions it will actually run against belong to people who cannot check it, because
checking it means already knowing which of their projects produce rules. An inference is
therefore untestable by the only person in a position to notice it was wrong.

Declaration puts the answer in the one place that cannot go stale. A project is created,
moved, renamed and retargeted over its life, and every one of those events invalidates a
list kept somewhere else while leaving the project's own file correct by construction.
This is the same argument that decides release-train membership, and the failure it guards
against is the same: a project missing from a list is silently absent from what the list
governs.

Declaration is also what makes a refusal possible, and the refusal is load-bearing. A tool
that infers can never report "you have not told me" — it can only report what it found, and
finding nothing is indistinguishable from there being nothing. Because the mechanism is a
declaration, a solution in which nobody declared is a question that was not answered rather
than an answer of zero, and the run can stop and name the property. That refusal is how a
user who has never heard of the property learns it exists, which matters because a property
nobody can discover is a property nobody will declare.

The cost accepted is real and falls entirely on the user: `--solution` reads nothing at all
until projects are edited, and the first encounter with the mechanism is a failed run. It
is accepted because the alternative on offer is not "works immediately" but "works
immediately, and is sometimes silently wrong in the one way this tool exists to prevent".

## Alternatives Considered

### Infer from a reference to Roslyn

Considered because it needs no cooperation from the user, matches the way analyzer projects
are actually built, and can be read from the same MSBuild evaluation the tool already
performs.

Rejected because it is not the same statement. Referencing Roslyn says a project *reads or
writes C#*, which is true of the tool's own worker, of a source generator, of a code-fix
assembly and of every test project that hosts a compilation. Measured here it selects six
projects to get one, and the five extra are not merely wasteful: each is an evaluation, and
some have no built output at all, so the run would fail on projects the user never intended
to include. The heuristic is also ambiguous before it is inaccurate, since deciding what
counts as a Roslyn reference means separating the compiler API from the analyzer packages
that share its name prefix.

### Infer from a type deriving from `DiagnosticAnalyzer`

Considered because it is the most precise signal available — it names the exact thing a
catalogue is generated from — and because the descriptors are read from such types anyway.

Rejected on two counts. It is still wrong here, selecting a test fixture alongside the real
analyzer, and the fixture is deliberately unconstructible, so the heuristic's one error is
also the input most likely to abort the run. More fundamentally, reading it requires the
project's output: deciding whether to read a project would mean having already located and
loaded what that project builds, which either forces `--solution` to build — losing the
property that makes validation safe against a working copy — or fails on precisely the
unbuilt projects that a solution-wide command is most likely to encounter.

### Reuse `EnforceExtendedAnalyzerRules`

Considered because it already exists, is already set on analyzer projects, and would
require no new property and no new documentation.

Rejected because it answers a different question. It states that a project should be
*checked by* the analyzer-authoring rules, not that it *produces* rules to catalogue; in
this repository the code-fix project sets it and declares no descriptor at all. Overloading
it would also make one property mean two things whose sets merely overlap today, so a user
who legitimately wanted one behaviour would silently acquire the other.

### Mark the produced assembly with an attribute

Considered because the repository already records provenance in assembly metadata, so the
mechanism would be familiar and would travel with the artifact rather than with the project
file.

Rejected because it is circular for this purpose. Reading an assembly attribute means
having built and located the project's output, which is the decision being made. It carries
the same consequence as the previous alternative — either `--solution` builds, or it fails
on unbuilt projects — and it would move the declaration out of the file a developer edits
into the artifact a build produces, which is the wrong direction for something a human has
to opt into.

### List the projects in the manifest

Considered because the manifest already declares every other fact about a catalogue, and it
would require no change to any project file.

Rejected because it re-creates the list that goes stale. A project renamed or moved leaves
the manifest wrong, and wrong in the silent direction. It also answers a different question
from the one asked: naming projects in the manifest is what `--project` already does, so
this alternative is `--project` with extra syntax rather than support for a solution.

### Read every project in the solution

Considered because it cannot guess short, which is the failure that matters most.

Rejected because it fails on the projects it should have ignored. A solution's test,
tooling and sample projects have outputs that may not be built, and each is a spawned
evaluation; a command that must succeed on every project in a solution before it can
catalogue one is less usable than a command that asks which one to read. It also gives up
the refusal: a solution where nothing produces rules would be read as an empty catalogue.

## Consequences

### Positive

* A catalogue generated from a solution contains the rules of exactly the projects the
  author named, and cannot silently lose one to a heuristic that failed to match.
* The mechanism cannot go stale as projects are created, renamed or moved, because the
  statement lives in the file that moves with them.
* A solution where nothing is declared is refused with a message that names the property,
  so the mechanism is discoverable from the failure rather than only from documentation.
* Solution acquisition inherits the existing project acquisition unchanged, including the
  property that it restores, builds and writes nothing.

### Negative

* `--solution` does nothing on a solution that has not been prepared, and the first
  encounter with the requirement is a failed run.
* The property is one more thing an analyzer author has to know about, and it is specific
  to this tool rather than a platform convention.
* An author who declares it on the wrong project gets a wrong catalogue with no warning —
  declaration removes the guessing, not the possibility of a mistaken answer.

### Risks

* A user meeting the refusal may read it as the feature being broken rather than as an
  instruction, if the message ever stops naming the property. That message is therefore
  part of the decision rather than an implementation detail, and is covered by tests.
* The property name is now a published contract in the same sense as a rule identifier:
  projects in other people's repositories declare it, so renaming it would break them
  silently — a solution would simply stop matching anything and be refused.
